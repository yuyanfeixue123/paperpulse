### 开头：用一个具体场景切入

> 早上八点半，邮箱里躺着一封邮件。
>
> 标题是「今日推荐 6 篇」。没有期刊宣传语，没有「Top 10 must-read」，没有广告。
>
> 每一篇都是同一个结构：标题一句话说清做了什么，DOI 可以直接点开，三行摘要，
> 最后一条 💡 是**推荐理由**——
>
> *「你关注街景图像与建成环境的定量评估，这篇用 MobileNetv3 做了跨城验证，
> 样本量 1.2 万户，比你订阅的三篇方法综述更进一步。」*
>
> 然后你往下划，发现整个列表里**没有一篇是你打算跳过的**。

**【写作提示】这是全文的钩子，下面这段转折必须接得快：**

我想说这个场景背后解决的问题。但先说说我为什么想做它。

做城乡规划的人大概都经历过同一件事：**读文献这件事，真正耗时间的不是读，是筛。**

导师丢给你一个方向，比如「用深度学习做城市更新」。你打开 Web of Science，
拟一个布尔检索式，搜出 1,847 条。你开始一个一个看标题——

看到第 40 条的时候你已经在摸鱼了。因为**你知道自己要什么，但查询语法不知道**，
而那 1,800 条里，真正值得你读的可能是 8 条。

于是你开始凑合：订阅几个期刊的 RSS，用关键词盯 arXiv，设几个 Google Scholar 提醒。
结果是每天几十封标题党邮件，真正想看的埋在里面，垃圾躺在上面。

我试过市面上几乎所有工具。它们的共同问题是**让人去做系统该做的事**——
写检索式、勾期刊、调参数。省下的时间其实没省下来，只是从「筛论文」
换成了「维护订阅规则」。

所以我想：**把 LLM 的开销，全部花在「筛掉论文」这一件事上。**

### 一、它是怎么工作的

**【写作提示】讲清楚，但别写成技术文档。主线是「一句话进去，邮件出来」。**

> 你用**一句话**描述研究方向。比如：
>
> *「我在读城市规划硕士，关心用街景图像和深度学习做建成环境评估，
> 也想看 15 分钟生活圈和公共交通可达性的研究。
> 不想看纯算法理论推导，也不想看医学图像分割。」*
>
> 然后系统做四件事：

**第一步：把这句话变成一份结构化画像。**

LLM 把这段话拆成中英双语关键词、排除项、arXiv 分类、检索式、相关度阈值。
不是你填表，是它读懂你的自然语言描述——生成之后你仍然可以逐项修改，
系统不会把你锁死在第一次的表述里。

**第二步：每 30 分钟，从 45 个数据源扫一遍新论文。**

arXiv、OpenAlex、Crossref、DOAJ、Europe PMC、bioRxiv、OSF……
Nature、Science、PNAS、Lancet、JAMA……

其中 **16 个免注册源默认开启**——装完什么都不用填，第一轮扫描就开始跑。
全部源都是官方 API 或官方 RSS（JournalTOCs 2026-09 已停止解析、Zetoc 2022 退役，
本项目不依赖任何第三方 TOC 聚合器），后台还可以添加任意 RSS/Atom 地址。

**第三步：两级过滤。**

先硬过滤（明显不相关的直接扔掉），再 SQLite FTS5 做 BM25 召回，
最后把候选的 20 篇交给 LLM 逐篇精排打分。

排序公式长这样：

```
final = 0.7 × LLM 打分 + 0.2 × 你的口味相似度 + 0.1 × 新鲜度 − 0.5（已推过）
```

**注意最后那项**——推过的论文会被降权，但不会消失。
因为一篇 seminal 的经典，你第二年还想再读一遍。

**第四步：每天定时投递到你邮箱。**

你点的每一个「有用 / 不感兴趣」，都会重塑下一次的画像。
打了一年的分，它就越懂你。

**顺带说一句模型兼容性，这对实际部署很重要：**
内置 DeepSeek、通义千问、Moonshot、智谱、硅基流动、OpenAI、Anthropic、Gemini、
Ollama（本地模型）九家预设，任何 OpenAI 兼容端点也能接入；
结构化输出做了三级降级（`json_schema` → `json_object` → 纯文本 + 服务端容错解析），
**几乎任何模型都能跑**——你手头有什么就用什么，不必为这个系统专门买某家的 API。

### 二、三个可能有争议的设计决定

**【写作提示】这部分是文章的技术含量所在。写出来能筛出真正的同类用户。**

#### ① 1 核 1G 就能跑，不要 Redis

现在提到「推荐系统」，默认配置都是 Redis + Celery + Postgres + 向量数据库。
但一个人用的推荐系统，需要这个吗？

PaperPulse 是**单进程**跑完所有事：uvicorn + APScheduler + 4 线程池。
任务队列用 SQLite 的 `task_runs` 表，进程崩了未完成任务还在表里，重启自动续跑。
数据库是 SQLite WAL 模式，常驻内存约 300MB。

不要 Redis 不等于裸奔。磁盘到 80% 自动收紧保留期、到 90% 停止采集保推送；
内存到 450MB 主动 GC、650MB 暂停采集；任务 600 秒软超时自动重置（重试 3 次后标失败），
systemd 配 60 秒看门狗，崩溃即拉起。**降级路径都是设计出来的，不是撞大运。**

**代价是什么？** 并发上不去，百人规模没问题，千人规模要重新设计。

**换来的是什么？** 一条命令装完，一台 20GB 的 VPS 就能跑。
不用管 Redis 挂没挂，不用看 Celery 的 flower 页面。
对自托管场景，这个取舍是对的。

#### ② 终端用户不需要 API Key

这是我认为最重要的一个决定。

很多同类工具的上手路径是：注册 → 绑定 Google Scholar → 去申请 OpenAI API Key →
填进去。每个 Key 都有免费额度，用完就要充值。**这对非技术用户是劝退的。**

PaperPulse 的做法：部署者一次性配好凭据（Fernet 加密存储），
用户**只需要注册一个账号就能用**。

那用户想用自己的 Key 怎么办？可以。在「账户」页填上自己的 API Key，
之后所有调用都走你自己的额度——而且**自带 Key 的用户不受每日调用次数限制**。
没有这个需求的就什么都不用管。

**同样的原则也写在配额上**：Brevo 免费 300 封/天是硬闸门，超限顺延次日，
**绝不静默丢弃**。系统宁愿晚发，也不会让你以为发了。

#### ③ 邮件发不出去的时候，系统会说实话

这个功能有点特别，我单独讲一下。

部分国内邮件通道有内容审核。如果一篇论文的标题里带了某些词，整封邮件会被**整封拒收**——
不是退信，就是丢进黑洞，你永远不知道为什么没收到。

PaperPulse 的处理：

1. 管理员可以配正则，命中的论文不进邮件正文，只在站内呈现
2. 邮件里会写「另有 3 篇未通过本邮件通道送达，登录查看完整推荐」
3. 更进一步——投递被拒时，系统用 LLM 猜候选词，
   再用**只含单个词的最小探测邮件**逐个试投，
   把稳定被拒的词沉淀成「通道词库」，下次自动避开

这个探测机制本身是克制的：**连续 2 次被拒才入库**（防止过滤器抖动误封），
探测邮件只发到部署者指定地址，**每日有封顶预算**——它不会变成一个乱发邮件的机器。

**实测很有意思**：阿里云通道逐词探测 8/8 全部放行，但整封投递 554 拒收。
说明它判定的是**组合语义**而不是单词黑名单。
系统检测到这种情况后，如实告诉你「逐词探测复现不了」——**而不是假装成功**。

> 顺带一提：那个词库功能一开始是为了绕过审核。做完之后我有点后悔——
> 因为它真正的价值其实是**透明**：让「为什么我收不到那几篇」变成一个可回答的问题。

### 四、安装

```bash
git clone https://github.com/yuyanfeixue123/paperpulse.git && cd paperpulse
sudo ./scripts/install.sh --repo https://github.com/yuyanfeixue123/paperpulse.git --domain papers.example.com
```

最低要求：**1 核 / 1GB 内存 / 20GB SSD / 一个域名**。

脚本会装依赖、建用户、生成密钥、配 systemd 和 Caddyfile、开机自启、
配每日 03:30 备份，最后进入配置向导。**可以重复执行**——
不会覆盖你已有的 `.env` 和数据。

没有浏览器？SSH 部署时域名往往还没就绪：

```bash
python -m app.cli setup      # 终端向导，ANSI 进度条 + 编号菜单，密码不回显
```

LLM 和邮件步骤会**先测连通性再允许你继续**——这一步挺重要，
不然填完一整套配置，最后发信失败才发现 Key 打错一个字母。

装完之后两条命令自检：

```bash
python -m app.cli verify-sources                    # 逐源连通性检查
python -m app.cli test-email --to you@example.com   # 发送测试邮件
```

后台的「系统自检」页还会一次检查出站网络、SMTP 出口、LLM、邮件通道、
数据源、磁盘、内存、时钟漂移与密钥——**部署成没成，它告诉你，不用你猜。**

### 五、它不能做什么

**【写作提示】写这一节比前面都重要。只讲好话的文章没人信。**

**未配 LLM 时中文召回有问题。**
本地分词产出中文关键词，但论文池是英文元数据，SQLite FTS5 默认分词器无法跨语言匹配。
配了 LLM 后会产出中英双语关键词，这个限制就消失了——但没配之前确实有。

**Brevo 免费版带 "Sent with Brevo" 角标。**
在意品牌干净就用 Resend（100 封/天，无角标），但额度少。

**退信 webhook 没实现。**
硬退信自动暂停需要 provider 侧 webhook 或 IMAP 轮询，目前得手动处理。

**中文源基本没有。**
ChinaXiv 接口不稳定（默认关闭），知网/万方/维普无开放 API——
这不是能绕过的版权和技术限制，**明确不做**。
需要中文文献请用 OpenAlex / Crossref 检索英文元数据。

**第三方 TOC 聚合器一个都不用。**
JournalTOCs 2026-09-06 已停止解析，Zetoc 2022 退役。
不依赖任何第三方聚合器，所有源都是官方 API 或官方 RSS。

**1 核 1G 的规模上限。**
并发上不去。百人规模没问题，千人规模要重新设计架构。

**DNS rebinding 的 TOCTOU 仍在。**
SSRF 防护会解析全部 A/AAAA 记录逐一判定、限制端口、逐跳校验重定向，
但校验后连接时 DNS 会二次解析——理论上仍有窗口。
单进程自部署场景影响有限，彻底解决需要做 IP pinning。

## 第二部分 · 短视频分镜脚本

**时长**：约 3 分 00 秒。平台限 2 分半时，砍掉镜头 4，压到 2 分 35 秒。
**形式**：屏幕录制 + 口播，不出镜。
**节奏**：前 15 秒三个硬切，不给观众滑走的机会。
**核心纪律**：所有画面都是真实运行的数据，不摆拍、不造假数字——
这条片子的可信度就是它的全部资产。

---

### 录制前的环境建设（先做完这一节，再开机）

**A. 演示数据（提前 1–2 天准备）**

1. 用真实域名部署一套演示环境（别用 example.com，画面里经不起看）。
2. 注册演示账号，提前建好 **3 个研究方向相近的订阅**——
   这样 `/stream` 里才会真实出现「3 个订阅同时命中」角标，镜头 1 和 6 要特写它。
3. 让系统真实跑一夜：第二天 `/feed` 和邮箱里都有真数据。
   **邮件必须真实收到，绝不伪造邮件截图。**
4. LLM、邮件凭据提前配好并测通（`python -m app.cli verify-sources`、`test-email`），
   避免录制时现场报错。
5. 评分演示前，给演示账号留几条未评分论文，保证镜头 6 有点击对象。

**B. 浏览器与桌面**

1. 1920×1080 录制；浏览器**无痕窗口**、隐藏书签栏、关闭通知、只开演示标签。
2. 页面缩放 **115%**（feed 页信息密度大，100% 在 1080p 下字太小；
   step2 表单可局部推到 125% 特写）。
3. 光标高亮开启（黄色圈），点击动效开启。

**C. 终端**

1. 字体 ≥18px、深色主题、窗口宽度收窄到 90 列以内（防止日志折行看不清）。
2. 预先 `cd` 到项目目录；`systemctl status` 停留在 active (running) 那一行。

**D. 文案与隐私**

1. 镜头 2 要**逐字打**示例句（打字画面比粘贴有说服力），文本提前写在便签里练两遍。
2. 真实邮箱地址、真实域名统一打码或用演示域名。
3. 限额数字用真实跑出来的数值——哪怕不好看。好数字靠提前养号，不靠改。

### 全片通用屏幕规范

- **转场只用两种**：硬切、0.3 秒推近。不要花哨转场。
- **关键数字双通道**：口播说一遍 + 画面字幕条复述一遍（如「45 源」「1 核 1G」「零 API Key」）。
- **圈选**：要指的东西用红框圈 0.5 秒，一屏最多圈一处。
- **字幕**：底部常驻主字幕；数字类字幕条放顶部，深底白字。
- **BGM** 低音量，口播段 ducking。

## 第四部分 · 发布文案的注意事项

**几个容易踩的坑：**

1. **别在标题里堆技术名词。** 「基于向量检索与大语言模型的学术文献智能推荐系统」——
   这种标题在公众号的推荐机制里是负分，写给谁看都不点。

2. **第一屏必须出现真实界面。** 公众号折叠阈值大约 200 字，
   纯文字的开头会被折起来，读者看不到你说什么。
   开头那张图就用素材清单的截图 1（`/stream`）。

3. **「它不能做什么」那一节别删。** 写了不足反而更可信。
   而且真有人看完那一节还愿意点的，才是真用户。

4. **数据要标来源和核实日期。** README 里 45 个源带 🟢🟡⚪ 三级可信度
   （已核实 / 按官方模板推导 / 待验证），核实日期 2026-10-03 就写在标题旁。
   这个细节写进文章里，能筛掉一批只看「star 数」的人。

5. **不要说「免费」或「无限」。** Brevo 免费版 300 封/天有硬上限，
   1 核 1G 的并发也有限。宣传话术要经得起实测。

6. **不要承诺中文文献。** 知网/万方/维普无开放 API，这是硬限制。
   写清楚比含糊过去更有说服力——学术用户最反感的就是这个。

7. **发布前重跑一遍数字核对清单。** 项目在更新，本文数字会过期。
   核对命令（2026-10-04 基准）：

   ```bash
   grep -rE "def test_" tests --include="*.py" | wc -l   # 195
   find app -name "*.py" | xargs wc -l | tail -1          # 13320
   python -c "import re;print(len(re.findall(r'\"[^\"]+\"', open('app/interest/presets.py', encoding='utf-8').read())))"   # 60
   grep -cE "^  - key:" config/sources.yaml               # 46（README 口径 45，需统一）
   ```

   安全审计条目（三轮 / 28 个 / 3 个严重）来自作者记录，git 可查到三轮审查的修复提交
   （如 d7957b0「修复第三轮审查发现的安全、功能与体验问题」）；
   若后续有第四轮，记得同步更新长文第六节和镜头 9 口播。

8. **所有演示画面必须来自真实运行。** 邮件真实收、数据真实跑、限额真实计数。
   这套宣传的立足点是「不完美但真实」——摆拍一旦被识破，第五节那段诚实就全白写了。
